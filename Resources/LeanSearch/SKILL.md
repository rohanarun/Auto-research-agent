name: lean-search
description: Generate standalone CPU search scripts and submit candidates to a shared Lean verification server, starting with QRH and extending through project-specific verification plans.
---

The native CPU Play button uses `.auto-research/cpu-search.json` (python, script and plan paths) and the generated script protocol documented in docs/lean-search.md. The bundled `cpu_search.py` and editable `qrh-cpu-plan.json` implement a finite exact QRH parameter grid, retaining every outcome and updating the UI overview. Do not automatically launch a model when setup is missing.

Use the adjacent `cli.py`; run `python3 -B cli.py --help` for commands. The harness installs this skill for local runs and Daytona workers. A standalone Claude session can read this file directly. Use repository evidence when generating a search script or editing its plan. The CPU search subtask executes that saved script directly with no model calls, model prompts or model fallback. Candidate generation and result summaries during the run come only from the script and its explicit configuration. Generating or changing a script is a separate development step.

For QRH, start with `qrh-track-a.json` and read its source, the current `auto-research.md`, `lean-tau/README.md`, and the actual certifier. Pin the certifier SHA-256, exact checkout revision, dependency lockfile and challenge. The example candidate is a historical baseline, not a target or record. Install SymPy only in the assigned workspace/runtime. Pass exact rational strings, the full theorem domain and a justified subdivision depth to `qrh-search --plan ... --output ...`. It checks F, J and every side constraint, preserves Bernstein boxes and failures, and emits EXACT_CONDITIONAL only. No found certificate is evidence of search failure, not an impossibility proof.

A previous QRH checker returned exit code zero while printing failed inequalities. Always inspect structured mathematical results. A finite CPU certificate is not a proof of the terminal analytic theorem. Previously this line was compared only against its own weaker baseline; compare like-for-like current theorem scope before claiming a record. Do not silently omit families or pole exceptions. Going beyond the old tau cap needs a tau-aware endpoint proof, the budget split, Euler region and row-norm obligations; a numeric substitution alone does not supply those proofs.

Prefer the shared server when a connection is supplied. `health --connection ...` lists installed profiles. Submit JSON `{"profile":"registered-name","files":{"Candidate.lean":"..."},"metadata":{"candidate":"exact parameters and source revision"}}` with `submit --connection ... --candidate ... --handle NEW_FILE`. Only the host operator installs profiles/commands/challenges; search nodes cannot weaken them. Poll with `status --connection ... --handle ...`. A timeout is not rejection: retain the handle and poll that UUID; never create a new job solely because an HTTP reply was lost. Only submit a new candidate after an evidence-based decision. Keep the token in its private file, never in prompt text or a repository.

When hosting, use the app's Lean server settings. Profiles use dedicated server-owned build directories and are serialized, keeping Lake caches between candidates. Never point them at a checkout with another writer. Prepare trusted dependencies ahead of time; verification runs with networking and unrelated file access denied. Freeze the exact challenge/audit and checker dependencies in `pins`, enumerate every terminal theorem in `targets`, and allow only candidate source files in `editable_files`. The server persists uploads, logs, source hashes, plans, receipts, and interrupted jobs; it restores original candidate files after each job. Closing the app should drain the owned service before exit.

`verify --plan ... --project ... --output ...` also works directly inside an assigned sandbox. LEAN_CHECKED means the specified build and axiom audit passed. COMPARATOR_ACCEPTED additionally requires the configured Comparator's acceptance markers and exit code. These receipts are bound to the supplied plan and source: they are not signatures or maintainer acceptance. Review the exact trusted plan, executable/tool pins, theorem statement, dependency provenance and sandbox configuration before a full formal claim. Without Comparator, report that missing check. Never turn fixture tests into QRH results.

Use `generic-plan.json` for other projects after inspecting their authoritative verifier. For integer multiplication, a numerical kappa candidate remains conditional unless a terminal proof discharges all claimed assumptions. For other inequality/finite certificate problems, prove the connection from the finite certificate to the requested theorem. Do not infer formal support merely from a project's name.

Agent37 and Daytona search nodes use the same HTTPS server API and do not need Lean. `remote.py` provides explicit-config control adapters for existing owned instances; API keys come from named environment variables. Do not provision, delete, or repeatedly launch nodes through these adapters. See current official Agent37 run-commands and Daytona process-execution docs before deployment. Preserve the node's configured model and resource budget.

Storage follows the user's assigned workspace. Keep generated artifacts and dependency caches outside Documents, Desktop and iCloud. A private remote node uses its assigned Linux filesystem. Update the research handoff with the failed experiment, evidence, and expected next behavior; do not add fixed search targets or automatic source rewrites to the harness.
